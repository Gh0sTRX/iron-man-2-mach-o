# 2026-10-29 — Mach-O loader handoff and verified blocker

## Confirmed source-level bug in MetalSyntax boilerplate

Upstream `master/source/macho.c` defines `segment_command` beginning with `char segname[16]`, but casts `d + off` (the beginning of the load command) to that type. Mach-O LC_SEGMENT begins with **two uint32 fields, cmd and cmdsize**; the segment name starts at byte offset +8. With the original Iron Man 2 1.0.0 binary, the upstream struct therefore reads segment names incorrectly (observed `\x01` rather than `__TEXT`/`__DATA`).

Minimal proposed patch (not yet Vita-tested):

```diff
 typedef struct {
+    uint32_t cmd, cmdsize;
     char segname[16];
     uint32_t vmaddr, vmsize, fileoff, filesize, maxprot, initprot, nsects, flags;
 } segment_command;
```

Review every use of this structure before compilation. Upstream: https://github.com/MetalSyntax/ios-loader-boilerplate/blob/master/source/macho.c

## Additional risks to test

1. `macho_run_inits` may double-add `MACHO_SLIDE` to function pointers already relocated by `apply_rebase`. Inspect section ownership and original pointer values.
2. `macho_load` obtains real Vita memory block pointers but uses `MACHO_SLIDE + vmaddr` in several places; confirm actual address mapping, don't assume.
3. Run upstream `master/tools/macho_prep.py` unmodified on the locally held original executable; compare its RBS1 output against our candidate.
4. Confirm ABI bridges: `r9`, softfp, 4-vs-8-byte stack alignment; audit missing imports against touchHLE, reuse license-compatible code.
5. Device log is the first real runtime milestone. Never claim a boot based on host analysis alone.
